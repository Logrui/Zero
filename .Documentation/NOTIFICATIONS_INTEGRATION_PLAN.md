# Notifications Integration Plan

Date: 2025-09-26

Purpose
-------
This document describes the current status and next steps to implement an integrated in-application notifications system for the Zero fork (staging branch). It focuses on in-app delivery (notification center + bottombar button), real-time delivery, persistence, developer tasks and rollout strategy.

High-level summary / current status
----------------------------------
- The UI contains a notifications button in the bottom bar (`apps/mail/components/app-bottombar.tsx`). It renders a `Bell` icon with a small badge dot but is not wired to any click handler or notification state.
- The codebase already includes a real-time messaging mechanism ("party"/socket messaging used by AI features) and server-side workflows for sync. Agent tooling exists that can trigger actions server-side (`apps/server/src/routes/agent/*`). These can be leveraged to push notifications.
- There is no dedicated `notifications` TRPC route, no DB schema for persisted notifications, and no service-worker or push subscription handling implemented yet.

Important refinement (separate notifications system)
-------------------------------------------------
Based on your clarification, this plan treats the notifications system as a distinct, first-class service (not a thin wrapper on the chat/agent messages). That means:

- Notifications are generated by multiple sources: agent/chat events, workflow automation (server-side jobs/workflows), external webhooks/HTTP callbacks, system alerts (connection failures, sync errors), and user-driven events (calendar reminders, scheduled digests).
- We will design notifications as a separate domain with its own DB schema, API surface, authorization model, ingestion pipeline, and real-time delivery mechanism. The existing party/socket system will remain a delivery channel (one of several) but will not be the sole authority for notifications.

This separation improves security (controlled ingestion points), reliability (idempotency, deduplication, persistence), and extensibility (external automation, 3rd-party integrations, push, and batch digests).

Goals
-----
1. Build a separate notifications domain (DB + API + ingestion) that supports multiple sources (workflows, webhooks, agents, system events) and multiple delivery channels (socket, push, email/digest).
2. Wire the bottombar notifications button to open a Notification Center (desktop and mobile) showing unread and recent notifications.
3. Persist notifications server-side so they survive page reloads and can be queried/filtered.
4. Deliver notifications in realtime using the existing party/socket system as one delivery channel. Optionally support push notifications (Service Worker + FCM / Web Push) in a follow-up phase.
5. Provide user controls: mark-as-read, dismiss, mute, per-source notification preferences, and global Do Not Disturb.
6. Support secure ingestion for automation workflows and external webhooks with idempotency, deduplication, and rate-limiting.

Design overview
---------------

Data model (example)
--------------------
Create a `notifications` table (Drizzle / Postgres) with the following minimal fields:

 - id: uuid (primary)
 - user_id: uuid (references users)
 - actor: text (who generated it: 'system', 'agent', 'gmail', 'calendar')
 - type: text (enum: 'mail', 'agent', 'calendar', 'system', 'connection')
 - title: text
 - body: text
 - metadata: jsonb (arbitrary payload e.g. { threadId, mailId, url })
 - is_read: boolean default false
 - created_at: timestamptz default now()
 - delivered_via: text[] (optional: 'socket','push')

Additional fields for workflow/webhook ingestion
-------------------------------------------------
- source_id: text NULLABLE — origin identifier for deduplication (e.g. webhook id, workflow run id)
- source_type: text — ('automation','webhook','agent','system','user') to allow filtering and preferences
- external_reference: text NULLABLE — opaque external id for tracing back to origin (e.g. third-party event id)
- metadata: jsonb (already listed) should contain the raw webhook payload or a minimal parsed subset; avoid storing large full payloads unless explicitly required by an opt-in flag.

APIs (server)
-------------
Implement TRPC endpoints (under `apps/server/src/trpc/routes/notifications.ts`):

 - notifications.list({ limit, cursor, unreadOnly, types }): paginated list for UI
 - notifications.markRead({ ids[] })
 - notifications.dismiss({ id })
 - notifications.subscribePreferences({ prefs }) (save per-user preferences)
 - notifications.create({ userId, type, title, body, metadata }) — internal (authenticated server/agent) route to create notifications

New ingestion endpoints (internal & external):

- notifications.createInternal({ userId, sourceType, sourceId, type, title, body, metadata }) — protected internal route for server workflows and agents. Requires service account credentials or internal auth.
- notifications.ingestWebhook({ signature, source, payload }) — exposed HTTP endpoint (e.g. `/api/notifications/webhook`) for third-party systems to post events. Responsible for signature verification, idempotency (by sourceId), minimal normalization, and enqueuing/persisting notifications.

Notes on ingestion design:
- The webhook ingestion endpoint should be small and idempotent: return 200 quickly after accepting or deduplicating. Use a write-ahead queue or immediate DB upsert keyed by (source, source_id) to deduplicate repeated callbacks.
- For automation workflows that run inside the system, prefer `createInternal` which is authenticated via internal service tokens and supports richer payloads and direct DB writes.

Server-side flow
----------------
1. Ingestion: notifications may be created via `createInternal`, from scheduled automation workflows, or via `ingestWebhook`. All ingestion paths normalize and persist a single canonical notification record (DB upsert keyed by `source_type+source_id` when present).
2. Dispatch: after persistence the server enqueues delivery tasks (synchronously or via a lightweight queue). Delivery tasks determine which channels to use (socket if connected, push if subscribed, email/digest if configured) and produce delivery attempts.
3. Delivery via Party: for real-time in-session delivery, the delivery task calls `getZeroSocketAgent(userConnectionId).broadcastChatMessage({ type: OutgoingMessageType.Notification, ...payload })` (or a new channel specifically for notifications). The Agent/ZeroDriver pattern is used to broadcast to all active client sessions for the user.
4. Fallback & offline: if socket delivery fails or the user has no active sessions, the server marks `delivered_via` accordingly and relies on `notifications.list` for clients to fetch missed notifications; optionally send push if subscriptions exist.
5. Idempotency & deduplication: the ingestion path must support idempotent writes (upsert by `source_type` + `source_id` or generating idempotency keys) and deduplicate notifications from retries or repeated webhook callbacks.

Real-time delivery options
-------------------------
- Use existing Party socket system (preferred): It is already used for mail/thread invalidation and AI messages; reuse channels or add a `Notification` message type. Prefer creating a dedicated `zero_notification` OutgoingMessage for clear separation from chat messages.
- Fallback: Poll `notifications.list` on client mount + reconnect (cheap when initial MVP).
- Push notifications (medium-term): implement Service Worker + Web Push (VAPID) + store subscriptions in DB. Useful for background notifications when the app isn't open.

Client UX & UI components
------------------------
1. Bottombar button (existing): wire the `Button` in `apps/mail/components/app-bottombar.tsx` to toggle Notification Center. Replace the static badge with a count from the notifications API.
   - ARIA: ensure `aria-label`, `aria-expanded` and `aria-controls` when menu open.
2. Notification Center component: new component under `apps/mail/components/ui/notification-center.tsx` that can render either a dropdown or a full panel (for mobile/responsive).
   - Use `ResizablePanel` pattern for desktop right-column or dropdown for compact mode.
   - Actions: mark read, dismiss, open (navigate to thread/calendar item), settings link.
3. Toasts: transient small toasts for immediate events (e.g., new mail while viewing another thread). Use existing `ui/toast.tsx` infrastructure.
4. Preferences UI: create a settings page `apps/mail/app/(routes)/settings/notifications/page.tsx` to configure per-source preferences and DND.

Additional client considerations for automation/webhooks
------------------------------------------------------
- When a webhook/automation event is received and persisted server-side, the real-time notification should include a light payload plus `metadata.summary` fields (threadId, url) for quick client actions. Avoid including full webhook body in socket payloads.
- Ensure the NotificationCenter UI supports filtering by `source_type` and quick actions that can call TRPC endpoints (e.g., `notifications.markRead`, `notifications.open` which can log an analytics event and optionally mark as read).
- Provide a developer-facing view (internal admin) to inspect raw webhook events, mapped notifications, and delivered statuses — useful for debugging automation workflows.

Security and privacy considerations
----------------------------------
- Minimize notification payloads: store full content server-side and only send lightweight metadata to clients. Avoid sending full email bodies in push messages.
- Authorization: ensure `notifications.list` and `create` are constrained to owner-only or service-accounts. Agent-created notifications must be vetted and rate-limited.
- External services: if implementing push or third-party integrations, document third-party data flows (Resend, Perplexity, ElevenLabs) and require opt-in.

Testing & QA
-----------

- E2E tests (packages/testing/e2e): add scenarios for new-notification, mark-read, dismiss and opening the notification. Reuse `packages/testing/e2e/auth.setup.ts` (better-auth) to simulate sessions.
- Performance: add load tests if notifications will be high-volume (e.g., agent actions). Ensure socket fan-out is scalable.

Updated migration & ops tasks for webhook-ready notifications
------------------------------------------------------------
4. Add a small `webhooks` table (or extend existing webhook tracking) to store webhook receipts and idempotency keys: `webhook_receipts(id, source, source_id, received_at, status, last_payload_summary)` so we can trace callbacks and avoid duplicates.
5. Add lightweight queueing / retry mechanism (in-process retry + durable queue if needed) for delivery attempts — consider Cloudflare Durable Objects / Workers Queues for resilient, serverless-friendly delivery.

Implementation roadmap (milestones & tasks)
-----------------------------------------
Phase 0 — Discovery (1-2 days)
 - Confirm Party/socket API shape and channel names (check `apps/mail/components/party.tsx` and server-side Party code).
 - Decide on push support (VAPID / FCM) and whether to scope to MVP.

Phase 1 — MVP (3-6 days)
 - DB migration & schema (create notifications table).
 - Server: create TRPC endpoints (list, markRead, create internal).
 - Client: implement `use-notifications` hook, wire bottombar badge count and toggle behavior to a `NotificationCenter` dropdown.
 - Implement real-time delivery via Party: add `Notification` message type; server publishes on create; client subscribes.
 - Add basic e2e tests for creating and reading a notification.

Phase 1 — Webhook & automation readiness (MVP extension)
- Add `notifications.ingestWebhook` HTTP handler (with signature verification and rate limiting) to accept incoming automation events and create normalized notifications.
- Add `webhook_receipts` table for idempotency and auditing.
- Implement `createInternal` for server workflows to create notifications programmatically.
- Test end-to-end: simulate workflow -> ingestWebhook -> persisted notification -> real-time broadcast -> client receives and displays.

Phase 2 — Quality & settings (2-4 days)
 - Preferences UI & per-source controls.
 - DND and mute functionality.
 - UI polish, accessibility (keyboard navigation, focus traps) and UX on mobile.

Phase 3 — Push + background (2-4 days + ops)
 - Implement Service Worker + Web Push subscription flow.
 - Store subscription in DB; server can send push messages for critical notifications.
 - Provide opt-in and privacy consent flows.

Phase 4 — Agent integration & telemetry (2-3 days)
 - Allow agents/tools to create notifications via secured endpoints.
 - Add PostHog/Sentry instrumentation for notification events (create/deliver/open) for analytics and debugging.

Risks & mitigations
-------------------
- Volume: high-frequency notifications may cause client overload. Mitigate by rate-limiting, collapsing similar notifications (e.g., mail threads summary), and offering user preferences to mute sources.
- Privacy: ensure notifications carry minimal data; link into app to view full content.
- Security: validate agent-originated notifications and require service-account authentication for programmatic creation.

Open questions
--------------
1. Do we want push support in MVP or deferred to Phase 3?
2. Are notifications per-user only, or should team/workspace notifications be supported to multiple recipients?
3. Should we surface notification history beyond X days (archival strategy)?

New open questions specific to automation/webhooks
-------------------------------------------------
4. What authentication form should webhooks use? HMAC signatures (recommended) or OAuth client credentials? HMAC allows the server to verify signature quickly; OAuth is more complex but can be used for multi-tenant integrations.
5. What is the expected event volume for automated workflows? This affects whether we implement a durable queue or simple DB + in-process dispatch for Phase 1.
6. Which events should be allowed to trigger notifications by default (and which require explicit opt-in/prefs)? For example: agent-run summaries might be opt-in, while connection failures should default to on.
